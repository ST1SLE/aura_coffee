# Product Design Document (PDD): Aura Coffee

## 1. System Vision & Purpose

Aura Coffee — это веб-платформа для локальной кофейни, обслуживающая два сценария: заказ с самовывозом (to-go) и доставку собственными курьерами. Платформа является production-системой для реальной кофейни с реальными клиентами.

### Что система делает

- **Онлайн-заказ**: клиент собирает корзину из меню (напитки с кастомизацией, еда, мерч), выбирает способ получения (самовывоз / доставка), указывает время и оплачивает онлайн.
- **Программа лояльности**: накопление баллов за оплаченные заказы и списание баллов для снижения стоимости следующих заказов.
- **Промокоды**: скидки по промокодам (процент или фиксированная сумма), управляемые администратором.
- **Личный кабинет**: авторизация по номеру телефона (SMS OTP), история заказов, баланс баллов, повторный заказ.
- **Админ-панель**: управление меню, заказами, пользователями, аналитика — с ролевой моделью (админ, бариста, курьер).
- **Двуязычность**: русский и английский интерфейс.

### Что система НЕ делает

- **Не является маркетплейсом.** Одна кофейня, одна точка, одно меню. Система не поддерживает мультитенантность и не предназначена для сетей.
- **Не агрегатор доставки.** Доставка осуществляется собственными курьерами кофейни. Интеграция с Яндекс.Едой, Delivery Club и прочими агрегаторами отсутствует.
- **Не предоставляет real-time трекинг.** Клиент видит статусы заказа (готовится, в пути, доставлен), но не позицию курьера на карте.
- **Не принимает наличные.** Оплата исключительно онлайн через платёжный шлюз.
- **Не мобильное приложение.** Система — веб-сайт, адаптированный под мобильные устройства (responsive web). Нативные iOS/Android приложения не предусмотрены.

## 2. Inviolable Rules

Эти правила имеют приоритет над любыми другими инструкциями. Агент ОБЯЗАН отклонить запрос, противоречащий этим ограничениям.

## 3. Domain Language & Definitions

Единый словарь терминов. Все переменные, таблицы БД, API-контракты и UI-лейблы ОБЯЗАНЫ использовать эти определения. Несоответствие терминологии — баг.

### Пользователи и роли

* **Customer (Клиент):** Зарегистрированный пользователь, авторизованный по номеру телефона через SMS OTP. Может просматривать меню, собирать корзину, оформлять и оплачивать заказы, накапливать и списывать баллы лояльности.
* **Admin (Администратор):** Сотрудник кофейни с полным доступом к админ-панели. Управляет меню, пользователями, промокодами, настройками системы (рабочие часы, радиус доставки, минимальная сумма, процент начисления баллов), просматривает статистику. Авторизуется отдельным механизмом (не SMS OTP клиента).
* **Barista (Бариста):** Сотрудник кофейни с ограниченным доступом к админ-панели. Видит входящие заказы, меняет статусы заказов, управляет стоп-листом. НЕ имеет доступа к управлению меню, пользователями, промокодами и настройками (см. INV-010).
* **Courier (Курьер):** Сотрудник доставки с минимальным доступом к админ-панели. Видит список доступных заказов на доставку, берёт заказ на себя, меняет статус доставки. НЕ имеет доступа ни к чему другому (см. INV-010).

### Меню и позиции

* **Category (Категория):** Группировка позиций меню. Четыре базовых типа: `DRINK` (напитки), `FOOD` (еда), `MERCH` (товары/мерч), `MODIFIER` (модификаторы). Категории управляются админом, имеют порядок сортировки и переводы на RU/EN.
* **Menu Item (Позиция меню):** Единица меню, принадлежащая одной категории. Содержит: название (RU + EN), описание (RU + EN), базовую цену, фото, флаг доступности (`available`). Позиция с `available = false` находится в стоп-листе (см. INV-006).
* **Modifier (Модификатор):** Опциональное дополнение к позиции меню (сироп, тип молока, доп. шот эспрессо). Имеет своё название, цену-надбавку и флаг доступности. Связь Menu Item ↔ Modifier — many-to-many: админ определяет, какие модификаторы доступны для каждой позиции.
* **Size Option (Размер):** Вариант объёма для напитков (S / M / L). Каждый размер имеет свою цену. Связан с конкретным Menu Item. Позиция без размеров продаётся по базовой цене.
* **Stop List (Стоп-лист):** Не отдельная сущность, а состояние Menu Item или Modifier: `available = false`. Бариста или админ переключает флаг. Позиция в стоп-листе отображается в меню как недоступная и не может быть добавлена в корзину.

### Корзина и заказ

* **Cart (Корзина):** Временная коллекция Cart Item'ов, привязанная к сессии клиента. Хранится в Redis (TTL). Не персистится в БД до оформления заказа. Корзина не имеет своего жизненного цикла — она либо конвертируется в Order, либо протухает.
* **Cart Item (Элемент корзины):** Одна строка корзины: ссылка на Menu Item + выбранный размер (если применимо) + набор выбранных модификаторов + количество. Итоговая цена Cart Item = (цена размера ИЛИ базовая цена) + сумма цен модификаторов) × количество.
* **Order (Заказ):** Подтверждённый и оплаченный набор позиций. Создаётся из Cart при оформлении. Содержит: снапшот позиций с ценами на момент оформления (цены не меняются ретроактивно), способ получения (`PICKUP` / `DELIVERY`), выбранное время, адрес (для доставки), применённый промокод, списанные баллы, итоговую сумму, статус (см. §6.1). Привязан к Customer по opaque ID.
* **Order Item (Позиция заказа):** Иммутабельный снапшот Cart Item на момент оформления. Содержит копии названий, цен и модификаторов — не ссылки. Гарантирует, что изменение меню не повлияет на историю заказов.

### Оплата и финансы

* **Payment (Платёж):** Запись об операции оплаты через ЮKassa. Привязана к Order. Содержит: сумму, статус (см. §6.2), внешний ID платежа ЮKassa, URL подтверждения. Один Order — один Payment (без частичных оплат).
* **Refund (Возврат):** Обратная операция к Payment через ЮKassa. Создаётся при отмене заказа клиентом (см. INV-005) или админом. Полный рефанд — единственный тип; частичные возвраты не поддерживаются.
* **Loyalty Account (Счёт лояльности):** Баланс баллов клиента. Один клиент — один счёт. Баланс не может быть отрицательным. Курс: 1 балл = 1₽. Начисление: `floor(сумма_деньгами × процент / 100)` после успешного завершения заказа (статус `COMPLETED`). Баллы бессрочные.
* **Loyalty Transaction (Транзакция лояльности):** Запись о начислении или списании баллов. Типы: `ACCRUAL` (начисление за заказ), `REDEMPTION` (списание при оплате), `REVERSAL` (возврат при отмене заказа), `ADMIN_ADJUSTMENT` (ручная корректировка админом). Каждая транзакция ссылается на Order (кроме `ADMIN_ADJUSTMENT`).
* **Promocode (Промокод):** Код на скидку, созданный админом. Атрибуты: код (уникальная строка), тип скидки (`PERCENT` / `FIXED_AMOUNT`), значение скидки, минимальная сумма заказа для применения (опционально), дата начала, дата окончания, лимит использований (общий), лимит использований на одного клиента, флаг активности. К заказу применяется максимум один промокод (см. INV-011).

### Доставка

* **Delivery Zone (Зона доставки):** Круговая зона с центром в координатах кофейни и настраиваемым радиусом (в км). Адрес клиента ОБЯЗАН попадать в зону для оформления доставки (см. INV-008).
* **Delivery Fee Rule (Правило стоимости доставки):** Настраиваемое правило: если сумма заказа ≥ порога — доставка бесплатна; если ниже — фиксированная стоимость доставки. Оба значения (порог и стоимость) настраиваются в админке.
* **Delivery Address (Адрес доставки):** Адрес клиента для доставки. Вводится через автокомплит Яндекс.Карт (Suggest API). Содержит: текстовый адрес, координаты (lat/lon), квартира/подъезд/этаж/комментарий курьеру. Клиент может сохранить несколько адресов в профиле.

### Уведомления

* **Notification (Уведомление):** Сообщение клиенту о смене статуса заказа. Доставляется по двум каналам: in-app (отображение на странице заказа) и SMS (через SMS.ru). In-app — всегда; SMS — для ключевых статусов (определяется в §6.1).

### Настройки системы

* **Shop Settings (Настройки кофейни):** Глобальные параметры, управляемые админом: рабочие часы (по дням недели), координаты кофейни, радиус доставки, минимальная сумма доставки, порог бесплатной доставки, стоимость доставки ниже порога, процент начисления баллов, время приготовления по умолчанию (для расчёта ASAP), оценка времени доставки (для расчёта ASAP при `type = DELIVERY`, default 30 мин).

## 4. Architectural Boundaries

Система разделена на логические модули с чёткими зонами ответственности. Тех. стек бэкенда и фронтенда — TBD (будет определён отдельно); данная секция описывает архитектурные границы, не привязываясь к конкретным фреймворкам.

### 4.1. Core API

* **Ответственность:** Центральный сервер приложения. Обрабатывает все HTTP-запросы от клиентского и админского фронтенда. CRUD операции для всех сущностей. Бизнес-логика: оформление заказа, расчёт стоимости (модификаторы + размер + доставка — промокод — баллы), валидация (стоп-лист, рабочие часы, радиус доставки, минимальная сумма). Управление сессиями и авторизацией (роли: customer, admin, barista, courier).
* **Владеет:** Всеми доменными сущностями из §3. Все state-мутации проходят через Core API.
* **Ограничения:**
  - Core API НЕ вызывает внешние API синхронно в рамках HTTP-запроса клиента (кроме Яндекс.Карт Suggest для автокомплита — допустимая задержка ≤ 500ms).
  - Платёжные операции (создание платежа, обработка webhook) и SMS-отправка делегируются воркерам через очередь задач.
  - Все финансовые мутации (списание баллов, применение промокода, создание Payment) — в рамках одной DB-транзакции (см. INV-004).
  - **Latency SLA:** Все API-эндпоинты ОБЯЗАНЫ отвечать в пределах 1000ms (p95) при нормальной нагрузке. Критический путь (создание заказа, обработка webhook ЮKassa) — ≤ 500ms (p95). Задачи, постановленные в очередь (payment creation, SMS) — ОБЯЗАНЫ быть взяты воркером в течение 5 секунд.

### 4.2. Payment Worker

* **Ответственность:** Взаимодействие с ЮKassa API. Создание платежа, обработка входящих webhook'ов от ЮKassa (подтверждение/отмена платежа), инициация рефанда.
* **Вход:** Задачи из очереди (Redis queue) от Core API, HTTP webhook'и от ЮKassa.
* **Выход:** Обновление статуса Payment и Order в БД (shared database).
* **Архитектура:** Payment Worker запускает два процесса: (1) Celery worker для асинхронных задач (создание платежа, инициация рефанда) и (2) легковесный HTTP-сервер (FastAPI) для приёма webhook'ов от ЮKassa. Webhook-эндпоинт (`POST /webhooks/yukassa`) принадлежит Payment Worker, НЕ Core API. Nginx маршрутизирует `/api/webhooks/yukassa` → Payment Worker HTTP. Обеспечивает полную изоляцию платёжной логики и централизованное логирование.
* **Ограничения:**
  - Webhook'и от ЮKassa ОБЯЗАНЫ верифицироваться по IP-whitelist (список IP из env var `YUKASSA_WEBHOOK_IPS`, см. §8.4) — MANDATORY. Верификация по подписи — MUST быть включена, если настроена в личном кабинете ЮKassa. Невалидные webhook'и — отклоняются (HTTP 403) с логированием.
  - Идемпотентность: повторный webhook с тем же `event_id` НЕ ДОЛЖЕН дублировать операцию.
  - Рефанд — полный (см. INV-005). Частичные рефанды не поддерживаются.

### 4.3. SMS Worker

* **Ответственность:** Отправка SMS через SMS.ru/SMSC API. Два типа сообщений: OTP-коды для авторизации и уведомления о статусе заказа.
* **Вход:** Задачи из очереди (Redis queue) от Core API.
* **Выход:** Статус доставки SMS (success/fail), логирование.
* **Ограничения:**
  - Rate-limiting на уровне Core API (см. INV-012), НЕ на уровне воркера. Воркер отправляет всё, что пришло в очередь.
  - Retry при сбое: 3 попытки с экспоненциальным backoff (2s, 8s, 32s). После 3 неудач — логирование ошибки, НЕ блокировка основного потока.
  - OTP-коды имеют TTL (определяется в §6.4). Воркер НЕ хранит коды — только передаёт.

### 4.4. Web — Customer Frontend

* **Ответственность:** Клиентский веб-интерфейс. Просмотр меню, кастомизация напитков, корзина, оформление заказа, выбор способа получения и времени, ввод адреса (Яндекс.Карты автокомплит), оплата (redirect на ЮKassa или встроенный виджет), личный кабинет (профиль, баллы, история, повторный заказ), страница статуса заказа.
* **Ограничения:**
  - Responsive web (mobile-first), НЕ нативное приложение. Минимальная поддерживаемая ширина viewport: 320px. Breakpoints: mobile (320–767px), tablet (768–1023px), desktop (≥ 1024px). Поддерживаемые браузеры: последние 2 версии Chrome, Safari, Firefox (mobile + desktop).
  - Двуязычный интерфейс (RU/EN). Переключение языка — на клиенте, тексты меню — из БД (RU + EN поля).
  - Все валидации — дублируются на сервере. Клиентские проверки (стоп-лист, радиус, рабочие часы) — UX-подсказки, не замена серверных.
  - Фронтенд НЕ хранит цены локально для расчётов — итоговая цена всегда приходит с сервера.
  - **Обновление статуса заказа:** Страница статуса заказа ОБЯЗАНА отображать актуальный статус с задержкой ≤ 10 секунд. Реализация: polling с интервалом 10s или WebSocket push (выбирается при реализации).

### 4.5. Web — Admin Panel

* **Ответственность:** Интерфейс для персонала кофейни. Единый UI с ролевой фильтрацией контента:
  - **Админ:** Управление меню (CRUD позиций, категорий, модификаторов, размеров, фото), управление заказами, управление пользователями (просмотр, баланс баллов, блокировка), промокоды (CRUD), настройки кофейни (Shop Settings), статистика/аналитика.
  - **Бариста:** Лента входящих заказов (принять → готовится → готов), стоп-лист (вкл/выкл позиций и модификаторов).
  - **Курьер:** Список доступных заказов на доставку, кнопка "взять заказ", смена статуса (забрал → доставил).
* **Ограничения:**
  - Ролевая фильтрация — и на клиенте (не показывать недоступные разделы), и на сервере (API отклоняет запросы вне роли — см. INV-010).
  - Авторизация персонала — отдельная от клиентской. Механизм TBD (логин/пароль или invite-ссылки от админа).
  - **Обновление ленты заказов:** Новые заказы (переход в `PAID`) ОБЯЗАНЫ появляться в ленте бариста в течение ≤ 5 секунд. Реализация: polling с интервалом 5s или WebSocket push (выбирается при реализации). Аналогично для ленты курьера.

### 4.6. Redis

* **Ответственность:** In-memory хранилище для данных с ограниченным сроком жизни и очередей задач.
* **Используется для:**
  - **Корзина (Cart):** Хранение Cart в Redis с TTL. Ключ: `cart:{session_id}`. При оформлении заказа — данные читаются из Redis, валидируются и персистятся в PG как Order/Order Items. Ключ удаляется после подтверждения оплаты (Order → `PAID`). При неудачной оплате (Order → `CANCELLED` из `CREATED`) корзина сохраняется — клиент может оформить заказ повторно без пересборки корзины.
  - **OTP-коды:** Хранение кодов подтверждения с TTL (определяется в §6.4). Ключ: `otp:{phone}`.
  - **Rate-limiting счётчики:** Счётчики SMS-запросов для INV-012. Ключи: `sms_rate:{phone}:minute`, `sms_rate:{phone}:hour`, `sms_rate:{phone}:day`.
  - **Очередь задач:** Задачи для Payment Worker и SMS Worker. Реализация через Redis-based queue (Celery, Bull, или аналог — зависит от стека).
  - **Сессии:** Хранение JWT refresh-токенов или session ID (механизм определяется при выборе стека).
* **Ограничения:**
  - Redis НЕ является источником истины для бизнес-данных. Все персистентные данные — в PostgreSQL.
  - Потеря данных Redis (перезагрузка без persistence) приводит к: потере корзин (клиент начинает заново), необходимости повторного OTP (не критично), пересозданию rate-limit счётчиков (временно ослабленная защита — приемлемо).

### 4.7. PostgreSQL

* **Ответственность:** Единственный источник истины для всех персистентных данных.
* **Хранит:** Users (PII — отдельная таблица, см. INV-013), Menu Items, Categories, Modifiers, Size Options, Orders, Order Items, Payments, Refunds, Loyalty Accounts, Loyalty Transactions, Promocodes, Delivery Addresses, Shop Settings, Notifications, Staff accounts.
* **Ограничения:**
  - Все финансовые операции — в рамках транзакций (см. INV-004).
  - Order Items — иммутабельные снапшоты. `UPDATE` на Order Items ЗАПРЕЩЁН.
  - Soft delete для пользователей (аноним-заглушка вместо удаления записи — см. INV-013).

## 5. Data Storage Strategy

PostgreSQL — единственный источник истины. Redis — эфемерное хранилище. Данная секция описывает ключевые решения по организации данных, не полную DDL-схему (она будет сгенерирована из этого описания при реализации).

### 5.1. Принципы

1. **Иммутабельность заказов.** Order и Order Items после создания НЕ обновляются через `UPDATE`. Статус Order меняется через отдельное поле `status`, но содержимое заказа (позиции, цены, модификаторы) — неизменяемо. Это гарантирует, что изменение меню не искажает историю.
2. **PII-изоляция (INV-013).** Персональные данные (телефон, имя, адреса) хранятся в отдельных таблицах (`user_profiles`, `delivery_addresses`). Таблицы заказов, платежей и лояльности ссылаются на пользователя по `user_id` (UUID, opaque). При удалении аккаунта PII-таблицы очищаются, `user_id` заменяется на tombstone-заглушку.
3. **Цены в копейках.** Все денежные значения хранятся как `INTEGER` в копейках (1₽ = 100). Это исключает ошибки округления с `FLOAT`. Отображение в рублях — ответственность фронтенда.
4. **Двуязычные поля.** Текстовые поля с переводами (название позиции, описание, название категории) хранятся парами: `name_ru`, `name_en`. Не JSONB, не отдельная таблица переводов — два явных столбца. Причина: всего 2 языка, простота запросов, типизация.
5. **Soft delete.** Удаление пользователей — через `deleted_at` timestamp + anonymization. Удаление позиций меню — через `available = false` (стоп-лист) или `archived = true` (скрыта из меню навсегда, но Order Items на неё ссылаются). Физический `DELETE` на бизнес-таблицах ЗАПРЕЩЁН.
6. **Timestamps.** Все таблицы содержат `created_at` и `updated_at` (UTC, `TIMESTAMPTZ`). Все временные значения хранятся и передаются в UTC. Конвертация в локальный часовой пояс — ответственность фронтенда.

### 5.2. Логические группы таблиц

#### Группа: Пользователи

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `users` | Аккаунт пользователя (клиент) | `id` (UUID PK), `phone_hash` (для lookup), `status` (ENUM: pending_verification/active/blocked/deleted, см. §6.5), `created_at`, `deleted_at` | — |
| `user_profiles` | PII клиента (изолировано) | `user_id` (FK → users), `phone` (encrypted), `display_name`, `preferred_language` (RU/EN) | 1:1 с users |
| `delivery_addresses` | Сохранённые адреса клиента | `id`, `user_id` (FK), `label`, `address_text`, `lat`, `lon`, `apartment`, `entrance`, `floor`, `comment`, `is_default` | N:1 с users |
| `staff_accounts` | Аккаунты персонала | `id` (UUID PK), `login`, `password_hash`, `role` (ENUM: admin/barista/courier), `display_name`, `is_active` | — |

**Примечания:**
- `users` и `staff_accounts` — две раздельные таблицы. Клиенты авторизуются по SMS OTP, персонал — по логину/паролю. Пересечения нет.
- `phone` в `user_profiles` хранится зашифрованным (AES-256-GCM; ключ — из env var `ENCRYPTION_KEY`, см. §8.4). `phone_hash` в `users` — для быстрого lookup при авторизации (SHA-256, без соли — нужен детерминированный поиск).

#### Группа: Меню

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `categories` | Категории меню | `id`, `type` (ENUM: drink/food/merch/modifier), `name_ru`, `name_en`, `sort_order`, `is_visible` | — |
| `menu_items` | Позиции меню | `id`, `category_id` (FK), `name_ru`, `name_en`, `description_ru`, `description_en`, `base_price` (int, копейки), `image_url` (legacy poster fallback), `media_type` (ENUM: image/video, nullable), `media_url`, `media_poster_url`, `available` (bool — стоп-лист), `archived` (bool), `sort_order` | N:1 с categories |
| `size_options` | Размеры напитков | `id`, `menu_item_id` (FK), `label` (S/M/L), `price` (int, копейки), `available` | N:1 с menu_items |
| `modifiers` | Модификаторы | `id`, `name_ru`, `name_en`, `price` (int, копейки), `available` | — |
| `menu_item_modifiers` | Связь позиция ↔ модификатор | `menu_item_id` (FK), `modifier_id` (FK) | M:N junction |

**Примечания:**
- Если у Menu Item есть Size Options — `base_price` игнорируется, цена берётся из выбранного Size Option.
- `archived = true` скрывает позицию из меню навсегда (не стоп-лист). Используется когда позиция больше не продаётся, но на неё ссылаются старые Order Items.
- Медиа позиции меню — презентационный слой. `media_type`, `media_url`, `media_poster_url` и legacy `image_url` НЕ участвуют в расчёте цены, доступности, корзины, платежа или Order Items snapshot.
- Видео напитков используются как ключевая часть customer UX: короткие owned/generated ролики, muted, looped, playsInline, с poster/fallback изображением. Видео другой кофейной сети, чужие брендинговые материалы и неочищенные сторонние ассеты ЗАПРЕЩЕНЫ.
- `media_url` может быть `NULL`. Если `media_type = video`, `media_poster_url` ОБЯЗАТЕЛЕН для первого кадра, reduced-motion fallback, ошибок загрузки и low-bandwidth режимов. Если новых media-полей нет, UI использует `image_url` как fallback.
- В v1 медиа хранятся как local static assets, потому что генерируются один раз и меняются редко. В БД сохраняются только публичные static paths вида `/media/menu/{slug}/hero.mp4` и `/media/menu/{slug}/poster.webp`; бинарные upload/storage-потоки не входят в v1.
- Admin menu editor ОБЯЗАН поддерживать редактирование `media_type`, `media_url`, `media_poster_url` и legacy `image_url`, но не загружает бинарные файлы. Подготовка/коммит/деплой generated assets — отдельный контентный шаг.
- Медиа URL в публичном меню не являются секретами. Нельзя возвращать приватные signed URLs, токены доступа или внутренние storage credentials в public menu response (INV-015).

#### Группа: Заказы

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `orders` | Заказы | `id` (UUID), `user_id` (FK → users), `status` (ENUM, см. §6.1), `type` (ENUM: pickup/delivery), `requested_time` (TIMESTAMPTZ, NULL = ASAP), `delivery_address_snapshot` (JSONB, копия адреса), `subtotal` (int), `discount_amount` (int), `points_used` (int), `delivery_fee` (int), `total` (int), `promocode_id` (FK, nullable), `created_at`, `updated_at` | N:1 с users |
| `order_items` | Позиции заказа (снапшот) | `id`, `order_id` (FK), `menu_item_name_ru`, `menu_item_name_en`, `size_label`, `unit_price` (int), `modifiers_snapshot` (JSONB: [{name_ru, name_en, price}]), `quantity`, `line_total` (int) | N:1 с orders |

**Примечания:**
- `order_items` хранит КОПИИ названий и цен, НЕ FK на menu_items. `UPDATE` на order_items ЗАПРЕЩЁН.
- `delivery_address_snapshot` — JSONB-копия адреса на момент заказа (адрес может быть удалён/изменён клиентом позже).
- `subtotal` = сумма `line_total` всех order_items. `total` = `subtotal` - `discount_amount` - `points_used` + `delivery_fee`.
- `requested_time = NULL` означает ASAP. Core API рассчитывает конкретное время при создании заказа и записывает его в `estimated_ready_at`.

#### Группа: Платежи

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `payments` | Платежи через ЮKassa | `id` (UUID), `order_id` (FK), `yukassa_payment_id` (external), `amount` (int), `status` (ENUM: pending/awaiting_confirmation/succeeded/payment_failed/refund_pending/refunded/refund_failed, см. §6.2), `confirmation_url`, `idempotency_key`, `created_at`, `updated_at` | 1:1 с orders |
| `refunds` | Возвраты через ЮKassa | `id`, `payment_id` (FK), `yukassa_refund_id` (external), `amount` (int), `status` (ENUM: pending/succeeded/failed), `reason`, `created_at` | N:1 с payments |

#### Группа: Лояльность

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `loyalty_accounts` | Баланс баллов клиента | `user_id` (FK → users, PK), `balance` (int, ≥ 0) | 1:1 с users |
| `loyalty_transactions` | История начислений/списаний | `id`, `user_id` (FK), `order_id` (FK, nullable), `type` (ENUM: accrual/redemption/reversal/admin_adjustment), `amount` (int, положительное для начисления, отрицательное для списания), `balance_after` (int), `description`, `created_at` | N:1 с users, N:1 с orders |

**Примечания:**
- `balance` в `loyalty_accounts` — денормализованная сумма. Источник истины — `loyalty_transactions`. При расхождении — пересчёт из транзакций.
- `CHECK (balance >= 0)` на уровне БД. Попытка списать больше баланса — DB error, ловится в транзакции (см. INV-004).

#### Группа: Промокоды

| Таблица | Назначение | Ключевые поля | Связи |
|---------|-----------|---------------|-------|
| `promocodes` | Промокоды | `id`, `code` (UNIQUE, upper-case), `discount_type` (ENUM: percent/fixed_amount), `discount_value` (int — процент или копейки), `min_order_amount` (int, nullable), `valid_from` (TIMESTAMPTZ), `valid_until` (TIMESTAMPTZ), `max_uses` (int, nullable), `max_uses_per_user` (int, nullable), `current_uses` (int, default 0), `is_active` (bool), `created_at` | — |
| `promocode_usages` | Журнал использований | `id`, `promocode_id` (FK), `user_id` (FK), `order_id` (FK), `created_at` | N:1 с promocodes, orders, users |

**Примечания:**
- Валидация промокода: `is_active = true` AND `valid_from ≤ now ≤ valid_until` AND `current_uses < max_uses` (если задан) AND кол-во записей в `promocode_usages` для этого user < `max_uses_per_user` (если задан) AND `order.subtotal ≥ min_order_amount` (если задан).
- `discount_type = percent`: скидка = `floor(subtotal * discount_value / 100)`. Процент не может превышать 100.
- `discount_type = fixed_amount`: скидка = `min(discount_value, subtotal)`. Скидка не может превышать сумму заказа.
- Жизненный цикл, удаление (archive-style), атомарный инкремент `current_uses` и правила редактирования — см. §6.6.

## 6. State Machines

Агент ОБЯЗАН сгенерировать state machine классы/enum'ы из этой секции. Любой переход, не указанный здесь — ЗАПРЕЩЁН.

### 6.1. Order Lifecycle (Жизненный цикл заказа)

**States:** `CREATED`, `PAID`, `PREPARING`, `READY`, `IN_DELIVERY`, `COMPLETED`, `CANCELLED`

**Initial state:** `CREATED` — создаётся при оформлении заказа (конвертация Cart → Order).

**Transitions:**

| From | To | Trigger | Precondition | Уведомления |
|------|----|---------|--------------|-------------|
| CREATED | PAID | ЮKassa webhook подтверждает оплату | Payment.status = `SUCCEEDED` | SMS + in-app: "Заказ оплачен" |
| CREATED | CANCELLED | Платёж не прошёл или истёк таймаут ожидания оплаты | Payment.status = `PAYMENT_FAILED`. Если баллы/промокод были зарезервированы — вернуть (см. INV-004) | In-app: "Платёж не прошёл" |
| PAID | PREPARING | Бариста нажимает "Готовится" | — | SMS + in-app: "Заказ готовится" |
| PAID | CANCELLED | Клиент отменяет заказ (см. INV-005) | Заказ ещё не в статусе PREPARING. Полный рефанд через ЮKassa + возврат баллов + возврат промокода | SMS + in-app: "Заказ отменён, средства возвращены" |
| PAID | CANCELLED | Админ отменяет заказ | Полный рефанд + возврат баллов + возврат промокода | SMS + in-app: "Заказ отменён кофейней" |
| PREPARING | READY | Бариста нажимает "Готов" | — | SMS + in-app: "Заказ готов" (для pickup: "Заказ готов, заберите") |
| PREPARING | CANCELLED | Админ отменяет заказ | Полный рефанд + возврат баллов + возврат промокода. Исключительная ситуация (напр. обнаружена невозможность приготовить) | SMS + in-app: "Заказ отменён кофейней" |
| READY | CANCELLED | Админ отменяет заказ | Полный рефанд + возврат баллов + возврат промокода. Исключительная ситуация (напр. клиент не забрал, заказ испорчен) | SMS + in-app: "Заказ отменён кофейней" |
| READY | IN_DELIVERY | Курьер берёт заказ на доставку | `order.type = DELIVERY`. Курьер нажимает "Взял" (см. §6.3) | In-app: "Курьер забрал заказ" |
| READY | COMPLETED | Бариста нажимает "Выдан" (pickup) | `order.type = PICKUP` | In-app: "Заказ завершён" |
| READY | COMPLETED | Автозакрытие по таймеру (pickup) | `order.type = PICKUP`. Прошло N минут с момента перехода в READY (N — настраиваемый, по умолчанию 60 мин). Логируется как `auto_completed = true` | — |
| IN_DELIVERY | COMPLETED | Курьер нажимает "Доставлен" | — | SMS + in-app: "Заказ доставлен" |

**Terminal states (нет исходящих переходов):**
- `COMPLETED` — заказ завершён (выдан / доставлен / автозакрыт). Баллы лояльности начисляются при переходе в этот статус.
- `CANCELLED` — заказ отменён. Рефанд инициирован, баллы и промокод возвращены.

**Forbidden transitions (явный запрет):**
- `COMPLETED → any`
- `CANCELLED → any`
- `PREPARING → PAID` (нельзя откатить готовку)
- `READY → PAID` / `READY → PREPARING` (нельзя откатить)
- `IN_DELIVERY → READY` (курьер не может вернуть)
- `IN_DELIVERY → CANCELLED` (заказ уже у курьера — отмена невозможна, решается оффлайн)

**Примечания:**
- `CREATED` — промежуточный статус между формированием заказа и получением подтверждения оплаты от ЮKassa. Клиент получает `confirmation_url` через polling `GET /api/v1/orders/{id}` (интервал 1-2с) и перенаправляется на страницу оплаты ЮKassa. Таймаут ожидания: 15 минут. Если webhook не пришёл за 15 мин — проверить статус через ЮKassa API, при отсутствии оплаты — перевести в CANCELLED.
- **Резервирование баллов и промокода:** При создании заказа (`CREATED`) баллы списываются немедленно через `loyalty_transaction` типа `RESERVATION` (баланс дебетуется). При подтверждении оплаты (`PAID`) — транзакция подтверждается (тип обновляется на `REDEMPTION`). При `CANCELLED` из `CREATED` — создаётся `REVERSAL`-транзакция, баланс восстанавливается. Промокод: `current_uses` инкрементируется при `CREATED`, декрементируется при `CANCELLED`.
- Корзина (Redis) удаляется после подтверждения оплаты (`PAID`). При неудачной оплате корзина сохраняется — клиент может попробовать снова.
- Если `total = 0` (полная оплата баллами, pickup или бесплатная доставка) — ЮKassa пропускается, Order переводится в `PAID` в той же DB-транзакции. Баллы списываются атомарно.
- Автозакрытие pickup-заказов реализуется через cron-задачу или delayed queue. Каждое автозакрытие логируется с `auto_completed = true` и `auto_completed_at` timestamp.

### 6.2. Payment Lifecycle (Жизненный цикл платежа)

**States:** `PENDING`, `AWAITING_CONFIRMATION`, `SUCCEEDED`, `PAYMENT_FAILED`, `REFUND_PENDING`, `REFUNDED`, `REFUND_FAILED`

**Initial state:** `PENDING` — создаётся одновременно с Order.

**Transitions:**

| From | To | Trigger | Precondition |
|------|----|---------|--------------|
| PENDING | AWAITING_CONFIRMATION | Core API создал платёж в ЮKassa, получил confirmation_url | — |
| PENDING | PAYMENT_FAILED | Вызов API ЮKassa для создания платежа не удался после 3 retry | Логируется ошибка. Триггерит Order: CREATED → CANCELLED |
| AWAITING_CONFIRMATION | SUCCEEDED | ЮKassa webhook: `payment.succeeded` | `idempotency_key` не обработан ранее |
| AWAITING_CONFIRMATION | PAYMENT_FAILED | ЮKassa webhook: `payment.canceled` или таймаут 15 мин | Триггерит Order: CREATED → CANCELLED |
| SUCCEEDED | REFUND_PENDING | Core API инициировал рефанд в ЮKassa | Order.status переходит в CANCELLED |
| REFUND_PENDING | REFUNDED | ЮKassa webhook: `refund.succeeded` | — |
| REFUND_PENDING | REFUND_FAILED | ЮKassa webhook: `refund.canceled` | Логируется ошибка, админ уведомляется |
| REFUND_FAILED | REFUND_PENDING | Админ инициирует повторный рефанд через админку | Создаётся новая запись в таблице `refunds`, повторный вызов ЮKassa API |

**Terminal states:**
- `REFUNDED` — деньги возвращены клиенту
- `PAYMENT_FAILED` — платёж не прошёл (деньги не списывались, терминальное состояние)

**Non-terminal failure:**
- `REFUND_FAILED` — рефанд не прошёл, деньги удержаны. Админ ОБЯЗАН разрешить ситуацию: повторный рефанд через систему или ручной возврат вне системы. Не является терминальным — допускает retry.

**Forbidden transitions:**
- `PAYMENT_FAILED → any` (платёж не прошёл, терминальное)
- `REFUNDED → any` (деньги возвращены, терминальное)
- `SUCCEEDED → AWAITING_CONFIRMATION` (нельзя откатить успешный платёж)
- `SUCCEEDED → PAYMENT_FAILED` (деньги уже списаны)
- `REFUND_FAILED → REFUNDED` (нельзя пометить как возвращённый без подтверждения ЮKassa)

### 6.3. Delivery Assignment Lifecycle (Жизненный цикл доставки)

**States:** `AWAITING_COURIER`, `COURIER_ASSIGNED`, `PICKED_UP`, `DELIVERED`, `CANCELLED`

**Initial state:** `AWAITING_COURIER` — создаётся когда Order переходит в `PREPARING` (только для `order.type = DELIVERY`).

Этот lifecycle параллелен Order Lifecycle для заказов с `type = DELIVERY`.

**Transitions:**

| From | To | Trigger | Precondition |
|------|----|---------|--------------|
| AWAITING_COURIER | COURIER_ASSIGNED | Курьер нажимает "Взять заказ" в своём интерфейсе | Заказ в списке доступных, ещё не взят другим курьером (optimistic lock) |
| AWAITING_COURIER | CANCELLED | Админ отменяет заказ (Order → CANCELLED) | Курьер ещё не назначен. Delivery Assignment отменяется вместе с заказом |
| COURIER_ASSIGNED | PICKED_UP | Курьер нажимает "Забрал" | Order.status = `READY`. Триггерит Order: READY → IN_DELIVERY |
| COURIER_ASSIGNED | CANCELLED | Админ отменяет заказ (Order → CANCELLED) | Курьер назначен, но ещё не забрал. Курьер уведомляется об отмене |
| PICKED_UP | DELIVERED | Курьер нажимает "Доставлен" | Триггерит Order: IN_DELIVERY → COMPLETED |

**Terminal states:**
- `DELIVERED` — заказ доставлен клиенту
- `CANCELLED` — заказ отменён админом до момента забора курьером

**Forbidden transitions:**
- `DELIVERED → any`
- `CANCELLED → any`
- `COURIER_ASSIGNED → AWAITING_COURIER` (курьер не может отказаться после взятия — решается оффлайн через админа)
- `PICKED_UP → COURIER_ASSIGNED` (нельзя откатить забор)
- `PICKED_UP → CANCELLED` (заказ уже у курьера — отмена невозможна, решается оффлайн)

**Примечания:**
- Optimistic lock при взятии заказа: два курьера одновременно нажимают "Взять" — первый выигрывает, второй получает ошибку "Заказ уже взят".

### 6.4. SMS OTP Lifecycle (Жизненный цикл OTP-кода)

**States:** `CREATED`, `SENT`, `VERIFIED`, `EXPIRED`, `FAILED`

**Initial state:** `CREATED` — создаётся после прохождения rate-limit проверки в Core API (см. INV-012). Rate-limit проверяется ДО создания OTP, не внутри lifecycle.

**Transitions:**

| From | To | Trigger | Precondition |
|------|----|---------|--------------|
| CREATED | SENT | SMS Worker успешно отправил SMS | — |
| CREATED | FAILED | SMS Worker не смог отправить (3 retry исчерпаны) | Логируется ошибка. Клиенту: "Не удалось отправить код, попробуйте позже" |
| SENT | VERIFIED | Клиент ввёл верный код | Код совпадает И TTL не истёк. Максимум 5 попыток ввода — после 5 неверных код аннулируется |
| SENT | EXPIRED | TTL истёк (5 минут) | Код удаляется из Redis |
| SENT | FAILED | 5 неверных попыток ввода | Код аннулируется. Клиент может запросить новый (с учётом rate-limit) |

**Terminal states:**
- `VERIFIED` — авторизация успешна, создаётся/возобновляется сессия
- `EXPIRED` — код протух
- `FAILED` — отправка не удалась или исчерпаны попытки ввода

**Forbidden transitions:**
- `VERIFIED → any`
- `EXPIRED → any`
- `FAILED → any`
- `CREATED → VERIFIED` (нельзя верифицировать до отправки)
- `CREATED → EXPIRED` (нельзя протухнуть до отправки)

**Параметры:**
- OTP: 6 цифр, криптографически случайный
- TTL: 5 минут
- Max attempts: 5 попыток ввода
- Rate-limit: см. INV-012 (1/мин, 5/час, 10/день)

### 6.5. User Account Lifecycle (Жизненный цикл аккаунта пользователя)

**States:** `PENDING_VERIFICATION`, `ACTIVE`, `BLOCKED`, `DELETED`

**Initial state:** `PENDING_VERIFICATION` — создаётся при первом запросе OTP на номер телефона. Запись `users` + `user_profiles` создаётся, но аккаунт не активен до верификации.

**Transitions:**

| From | To | Trigger | Precondition |
|------|----|---------|--------------|
| PENDING_VERIFICATION | ACTIVE | OTP успешно верифицирован (§6.4: SENT → VERIFIED) | Создаётся `loyalty_accounts` (баланс 0). Аккаунт полностью активен |
| ACTIVE | BLOCKED | Админ блокирует пользователя | Система автоматически отменяет все активные заказы пользователя (не в COMPLETED/CANCELLED) с полным рефандом (см. §7.6). Заблокированный пользователь не может авторизоваться и создавать заказы |
| BLOCKED | ACTIVE | Админ разблокирует пользователя | — |
| ACTIVE | DELETED | Клиент запрашивает удаление аккаунта | Система автоматически отменяет все активные заказы с полным рефандом. PII удаляется (см. INV-013). Баланс баллов обнуляется. Действие необратимо |
| BLOCKED | DELETED | Админ удаляет заблокированного пользователя | PII удаляется, баллы обнуляются |

**Terminal states:**
- `DELETED` — необратимо. PII удалены, `user_id` заменён на tombstone

**Forbidden transitions:**
- `DELETED → any`
- `PENDING_VERIFICATION → BLOCKED` (нельзя заблокировать неверифицированный аккаунт)
- `PENDING_VERIFICATION → DELETED` (нет PII для удаления, запись просто не создаётся)
- `BLOCKED → PENDING_VERIFICATION` (нельзя откатить верификацию)
- `ACTIVE → PENDING_VERIFICATION` (нельзя откатить верификацию)

### 6.6. Promocode Lifecycle (Жизненный цикл промокода)

**States:** `INACTIVE`, `ACTIVE`, `EXPIRED`, `EXHAUSTED`

**Storage:** Отдельная `status`-колонка НЕ заводится. В БД хранятся только `is_active` (bool) + `valid_from` / `valid_until` + `current_uses` / `max_uses`. `EXPIRED` и `EXHAUSTED` ВЫЧИСЛЯЮТСЯ на чтении; `INACTIVE` ↔ `ACTIVE` управляются через `is_active`. `INACTIVE` покрывает и "новый / ещё не активированный", и "админ деактивировал" — различать черновик и паузу не требуется.

**Маппинг state → условие (порядок проверки сверху вниз):**

| State | Условие |
|-------|---------|
| EXPIRED   | `valid_until IS NOT NULL AND now > valid_until` (приоритет над остальными) |
| EXHAUSTED | не EXPIRED AND `max_uses IS NOT NULL AND current_uses ≥ max_uses` |
| ACTIVE    | не EXPIRED AND не EXHAUSTED AND `is_active = true` AND (`valid_from IS NULL OR now ≥ valid_from`) |
| INACTIVE  | иначе (`is_active = false`, либо `now < valid_from`) |

**Initial state:** `INACTIVE` — промокод создаётся админом с `is_active = false`. Активация — отдельное действие.

**Transitions:**

| From | To | Trigger | Precondition |
|------|----|---------|--------------|
| INACTIVE | ACTIVE | Админ активирует (`is_active = true`) | `valid_until` задан, `discount_value > 0`, не EXPIRED, не EXHAUSTED |
| ACTIVE | INACTIVE | Админ деактивирует (`is_active = false`) | — |
| ACTIVE | EXPIRED | `now > valid_until` | Вычисляется при чтении. Cron-синхронизация не требуется (опциональная подчистка — §7.1 Phase 6) |
| ACTIVE | EXHAUSTED | `current_uses ≥ max_uses` | Атомарный conditional UPDATE в checkout (см. ниже) |
| INACTIVE | EXPIRED | `now > valid_until` | Вычисляется при чтении |
| EXHAUSTED | ACTIVE | Отмена заказа освободила слот (§7.6) | `current_uses < max_uses` после декремента, не EXPIRED, `is_active = true` |

**Terminal states:**
- `EXPIRED` — срок действия истёк. Необратим: нельзя "продлить", нужно создать новый промокод.

**Non-terminal exhaustion:**
- `EXHAUSTED` — лимит исчерпан, но может вернуться в `ACTIVE` при отмене заказа (§7.6, шаг 2).

**Forbidden transitions:**
- `EXPIRED → any` — истёкший нельзя реактивировать.
- Одновременный EXPIRED + EXHAUSTED невозможен по определению: EXPIRED имеет приоритет в маппинге.

**Атомарный инкремент `current_uses`:**
- Checkout ОБЯЗАН инкрементировать счётчик через conditional UPDATE:
  ```sql
  UPDATE promocodes SET current_uses = current_uses + 1
  WHERE id = :id AND (max_uses IS NULL OR current_uses < max_uses)
  RETURNING *;
  ```
- Нулевое количество обновлённых строк → параллельный checkout забрал последний слот → текущая транзакция откатывается с ошибкой квоты. Простой SELECT-then-UPDATE ЗАПРЕЩЁН (INV-004).

**Удаление (archive-style):**
- Физический `DELETE` промокодов ЗАПРЕЩЁН. FK `promocode_usages → promocodes` с `ondelete=RESTRICT` обеспечивает это на уровне БД.
- "Удалить" промокод = деактивировать (`is_active = false`). Админский UI не показывает кнопку Delete.

**Редактирование:**
- `current_uses = 0`: админ МОЖЕТ изменить ЛЮБОЕ поле (`code`, `discount_type`, `discount_value`, даты, лимиты, `min_order_amount`, `is_active`).
- `current_uses > 0`: редактируемы ТОЛЬКО `valid_until`, `max_uses`, `max_uses_per_user`, `min_order_amount`, `is_active`. Поля `code`, `discount_type`, `discount_value` — read-only. Причина: исторические `promocode_usages` и `orders` ссылаются на промокод; изменение скидочного значения задним числом искажает аудит, чеки клиентов и бухгалтерскую историю (родственно INV-014).
- Переключение `is_active` разрешено в любом не-EXPIRED состоянии — это lifecycle-переход, а не редактирование полей.

### 7.2. Order Pricing Chain

Определяет порядок расчёта итоговой стоимости заказа. Агент ОБЯЗАН реализовать шаги в указанном порядке. Каждый шаг зависит от результата предыдущего.

1. **Subtotal** — сумма всех позиций в корзине.
   Для каждого Cart Item: `line_total = (size_price ИЛИ base_price + Σ modifier_prices) × quantity`.
   `subtotal = Σ line_total`.
   → Все цены берутся из БД на момент расчёта (не из кэша клиента). Если позиция в стоп-листе — ОТКЛОНИТЬ заказ (см. INV-006).

2. **Промокод (если применён)** — рассчитать скидку.
   → Валидация промокода: статус `ACTIVE`, `valid_from ≤ now ≤ valid_until`, `current_uses < max_uses`, кол-во использований пользователем < `max_uses_per_user`, `subtotal ≥ min_order_amount`.
   → `discount_type = PERCENT`: `discount = floor(subtotal × discount_value / 100)`.
   → `discount_type = FIXED_AMOUNT`: `discount = min(discount_value, subtotal)`.
   → `after_promo = subtotal - discount`.
   → Если промокод невалиден — ОТКЛОНИТЬ с причиной. НЕ игнорировать молча.

3. **Баллы (если клиент списывает)** — рассчитать списание.
   → `max_redeemable = min(customer.loyalty_balance, after_promo)`. Клиент может списать до 100% оставшейся суммы (см. решение из интервью).
   → `points_used = min(requested_points, max_redeemable)`. Если клиент запросил больше баланса — использовать весь баланс, не ошибку.
   → `after_points = after_promo - points_used`.

4. **Стоимость доставки (если `type = DELIVERY`)** — рассчитать доставку.
   → Delivery Fee Chain (§7.4).
   → `delivery_fee` = результат chain.
   → Для `type = PICKUP`: `delivery_fee = 0`.

5. **Итого** — финальная сумма к оплате.
   → `total = after_points + delivery_fee`.
   → `total` — это сумма, которая уходит в ЮKassa.
   → Если `total = 0` (полная оплата баллами, pickup или бесплатная доставка) — создать платёж на 0₽? **НЕТ.** Если `total = 0`, пропустить ЮKassa, перевести Order сразу в `PAID`. Баллы списываются атомарно в той же транзакции.

6. **Начисление баллов (отложенное)** — расчёт будущего начисления.
   → `accrual = floor(money_paid × loyalty_percent / 100)`, где `money_paid = total` (фактически оплаченная деньгами часть, т.е. `after_points + delivery_fee`... нет — баллы начисляются на стоимость товаров, оплаченную деньгами, БЕЗ стоимости доставки).
   → Уточнение: `money_paid = after_points` (сумма за товары после вычета промокода и баллов, БЕЗ delivery_fee). Доставка — это услуга, не покупка товаров кофейни.
   → `accrual = floor(money_paid × loyalty_percent / 100)`.
   → Начисление происходит НЕ сейчас, а при переходе Order в `COMPLETED` (см. §6.1). Значение `accrual` сохраняется в Order для отображения клиенту ("Вы получите X баллов за этот заказ").

### 7.3. Address Validation Chain

Определяет порядок валидации адреса доставки. Выполняется при оформлении заказа с `type = DELIVERY`.

1. **Автокомплит (клиентская сторона)** — клиент вводит адрес, Яндекс.Карты Suggest API возвращает варианты.
   → Клиент выбирает вариант → на клиент возвращаются координаты (lat/lon) и текст адреса.
   → Это UX-подсказка, НЕ валидация. Переход к шагу 2.

2. **Серверный геокодинг** — Core API получает адрес от клиента.
   → Если клиент передал координаты (lat/lon) из автокомплита — использовать их.
   → Если координат нет (пользователь ввёл адрес вручную, обойдя автокомплит) — вызвать Яндекс.Карты Geocoder API для получения координат.
   → Geocoder не нашёл адрес или вернул низкую точность (`precision` < `street`): ОТКЛОНИТЬ. Ошибка: "Не удалось определить точный адрес. Пожалуйста, уточните."
   → Координаты получены: переход к шагу 3.

3. **Проверка радиуса** — вычислить расстояние от кофейни до адреса клиента.
   → Формула: Haversine distance между `(shop_lat, shop_lon)` и `(address_lat, address_lon)`.
   → `distance ≤ delivery_radius_km`: адрес в зоне доставки. ПРИНЯТЬ.
   → `distance > delivery_radius_km`: ОТКЛОНИТЬ. Ошибка: "Адрес за пределами зоны доставки (максимум {radius} км)."

4. **Сохранение** — если валидация прошла, предложить клиенту сохранить адрес в профиле (если ещё не сохранён).

### 7.4. Delivery Fee Chain

Определяет стоимость доставки. Вызывается из Order Pricing Chain (§7.2, шаг 4).

1. **Проверка минимальной суммы** — `subtotal` (до вычета промокода и баллов) сравнивается с `min_delivery_amount` из Shop Settings.
   → `subtotal < min_delivery_amount`: ОТКЛОНИТЬ заказ на доставку. Ошибка: "Минимальная сумма заказа для доставки — {min}₽". Вернуть клиента к корзине. НЕ предлагать самовывоз автоматически — клиент решает сам.
   → `subtotal ≥ min_delivery_amount`: переход к шагу 2.

2. **Расчёт стоимости** — `subtotal` (до вычета промокода и баллов) сравнивается с `free_delivery_threshold` из Shop Settings.
   → `subtotal ≥ free_delivery_threshold`: `delivery_fee = 0`. Бесплатная доставка.
   → `subtotal < free_delivery_threshold`: `delivery_fee = shop_settings.delivery_fee` (фиксированная стоимость). Клиенту показать: "До бесплатной доставки не хватает {diff}₽".

---

### 7.5. Time Slot Validation Chain

Определяет валидацию выбранного времени получения заказа. Выполняется при оформлении заказа.

1. **Определение типа времени** — клиент выбрал ASAP или конкретное время?
   → ASAP: переход к шагу 2.
   → Конкретное время: переход к шагу 3.

2. **Расчёт ASAP** — определить ближайшее доступное время.
   → `estimated_time = now + default_prep_time_minutes` (из Shop Settings).
   → Для `type = DELIVERY`: `estimated_time += estimated_delivery_time_minutes` (из Shop Settings, default 30 мин).
   → Проверить, попадает ли `estimated_time` в рабочие часы (из `working_hours` в Shop Settings):
     → Попадает: `requested_time = estimated_time`. ПРИНЯТЬ.
     → Не попадает (кофейня закрыта): найти ближайшее открытие.
       → Ближайшее открытие ≤ 24ч: `requested_time = opening_time + default_prep_time`. Показать клиенту: "Кофейня сейчас закрыта. Ближайшее время: {time}". Клиент подтверждает или выбирает другое время.
       → Ближайшее открытие > 24ч: ASAP недоступен. Клиент ОБЯЗАН выбрать конкретное время (переход к шагу 3). Показать: "ASAP недоступен. Выберите время." (см. INV-007).

3. **Валидация конкретного времени.**
   → `requested_time` в прошлом: ОТКЛОНИТЬ. "Выберите время в будущем."
   → `requested_time < now + default_prep_time_minutes`: ОТКЛОНИТЬ. "Минимальное время приготовления — {N} минут. Выберите более позднее время."
   → `requested_time` вне рабочих часов: ОТКЛОНИТЬ. "Кофейня не работает в выбранное время. Рабочие часы: {schedule}." (см. INV-007).
   → Все проверки пройдены: ПРИНЯТЬ.

### 7.6. Order Cancellation Chain

Определяет логику отмены заказа. Отмена — критическая финансовая операция. Все шаги — в одной DB-транзакции (см. INV-004).

1. **Проверка права на отмену.**
   → Клиент: может отменить только если `order.status = PAID` (см. INV-005).
   → Админ: может отменить в статусах `PAID`, `PREPARING`, `READY`. НЕ может отменить `IN_DELIVERY`, `COMPLETED`, `CANCELLED`.
   → Нет права: ОТКЛОНИТЬ с причиной.

2. **Возврат промокода (если был применён).**
   → Декрементировать `promocode.current_uses`.
   → Удалить запись из `promocode_usages`.
   → Если промокод был `EXHAUSTED` и `current_uses < max_uses` после декремента и `valid_until` ещё не наступил — перевести в `ACTIVE` (см. §6.6: EXHAUSTED → ACTIVE). Если `valid_until` истёк — перевести в `EXPIRED`.

3. **Возврат баллов (если были списаны).**
   → Создать `loyalty_transaction` типа `REVERSAL` на сумму списанных баллов.
   → Инкрементировать `loyalty_account.balance`.

4. **Инициация рефанда (если был платёж).**
   → Если `payment.amount > 0`: создать рефанд в ЮKassa API. Payment → `REFUND_PENDING`.
   → Если `payment.amount = 0` (заказ был оплачен полностью баллами): рефанд не нужен.

5. **Смена статуса заказа.**
   → `order.status = CANCELLED`.
   → `order.cancelled_by = customer | admin`.
   → `order.cancelled_at = now`.

6. **Уведомление.**
   → SMS + in-app: "Заказ #{id} отменён. Средства будут возвращены."
   → Если отмена админом — указать причину (если указана).

### 7.7. Repeat Order Chain

Определяет логику повторного заказа из истории.

1. **Клиент нажимает "Повторить заказ"** — система получает `order_id` из истории.

2. **Валидация позиций** — для каждого Order Item найти текущий Menu Item по `menu_item_id` (сохранён в Order Item как reference).
   → Позиция найдена, `available = true`, `archived = false`: добавить в корзину с ТЕКУЩЕЙ ценой (не исторической).
   → Позиция в стоп-листе (`available = false`): пропустить, уведомить клиента: "{name} сейчас недоступен".
   → Позиция архивирована (`archived = true`): пропустить, уведомить: "{name} больше не в меню".
   → Модификатор недоступен: пропустить модификатор, уведомить. Позицию добавить без этого модификатора.
   → Размер недоступен: пропустить позицию целиком, уведомить.

3. **Результат.**
   → Хотя бы одна позиция добавлена: открыть корзину. Показать список пропущенных позиций (если есть).
   → Ни одна позиция не добавлена: показать ошибку: "К сожалению, ни одна позиция из этого заказа сейчас недоступна."
   → НЕ оформлять заказ автоматически. Клиент просматривает корзину, может изменить, и затем оформляет сам.

### 7.8. SMS Delivery Chain

Определяет порядок отправки SMS. Применяется к OTP и уведомлениям о статусе.

1. **Rate-limit проверка (только для OTP)** — Core API проверяет счётчики в Redis (см. INV-012).
   → Лимит не превышен: поставить задачу в очередь SMS Worker. Инкрементировать счётчики.
   → Лимит превышен: ОТКЛОНИТЬ. Ошибка: "Слишком много запросов. Попробуйте через {seconds} сек."
   → Для уведомлений о статусе: rate-limit НЕ проверяется (уведомления — инициированы системой, не клиентом).

2. **SMS Worker отправляет SMS** через SMS.ru API.
   → Успех (HTTP 200, статус `OK`): пометить Notification как `sent`. Done.
   → Ошибка: retry с экспоненциальным backoff (2s, 8s, 32s).

3. **Retry исчерпаны (3 попытки).**
   → Для OTP: пометить OTP как `FAILED`. Клиенту: "Не удалось отправить код. Попробуйте позже."
   → Для уведомлений: пометить Notification как `failed`. Логировать. НЕ блокировать основной поток (заказ продолжает обрабатываться).
   → НЕ молчать — ошибка ОБЯЗАНА быть залогирована.

### 7.9. Payment Webhook Processing Chain

Определяет обработку входящих webhook'ов от ЮKassa. Критическая цепочка — ошибка здесь = потеря денег или заказа.

1. **Верификация webhook'а.**
   → Проверить IP-адрес отправителя (список IP ЮKassa) ИЛИ подпись (если настроена).
   → Невалидный: ОТКЛОНИТЬ (HTTP 400). Логировать как потенциальную атаку.
   → Валидный: переход к шагу 2.

2. **Идемпотентность.**
   → Проверить `event_id` webhook'а — обработан ли ранее.
   → Уже обработан: вернуть HTTP 200 (ЮKassa не будет повторять). Done.
   → Новый: сохранить `event_id`, переход к шагу 3.

3. **Обработка события.**
   → `payment.succeeded`: обновить Payment → `SUCCEEDED`. Обновить Order → `PAID`. Фактически списать зарезервированные баллы и промокод. Отправить уведомление клиенту.
   → `payment.canceled`: обновить Payment → `PAYMENT_FAILED`. Обновить Order → `CANCELLED`. Вернуть зарезервированные баллы и промокод. Отправить уведомление.
   → `refund.succeeded`: обновить Payment → `REFUNDED`. Логировать.
   → `refund.canceled`: обновить Payment → `REFUND_FAILED`. Логировать ошибку, уведомить админа. Требуется ручное разрешение (повторный рефанд или возврат вне системы).
   → Неизвестный тип: логировать, вернуть HTTP 200 (не провоцировать retry).

4. **Ответ ЮKassa.**
   → Всегда HTTP 200 после успешной обработки. ЮKassa повторяет при non-200 (до 10 раз в течение 24ч).
   → Если обработка упала с ошибкой — НЕ возвращать 200. Позволить ЮKassa повторить.

## 8. External API Compliance

Данная секция описывает правила взаимодействия с внешними сервисами. Все интеграции ОБЯЗАНЫ соответствовать условиям использования (ToS) соответствующих сервисов.

### 8.1. ЮKassa

**Назначение:** Приём онлайн-платежей и рефандов. Единственный платёжный шлюз (см. INV-001).

**Используемые API:**
- `POST /v3/payments` — создание платежа. Вызывается из Payment Worker при оформлении заказа.
- `GET /v3/payments/{id}` — проверка статуса платежа. Вызывается при таймауте webhook'а (15 мин, см. §6.1).
- `POST /v3/refunds` — создание полного возврата. Вызывается при отмене заказа (см. §7.6).
- Webhooks — входящие уведомления от ЮKassa о смене статуса платежа/рефанда (см. §7.9).

**Ограничения:**
- **Idempotency key:** Каждый запрос на создание платежа ОБЯЗАН содержать уникальный `Idempotency-Key` (UUID). Повторный запрос с тем же ключом — безопасен (ЮKassa вернёт тот же результат).
- **Webhook endpoint:** Единый `POST /api/webhooks/yukassa`. Доступен без аутентификации (ЮKassa не отправляет токены), но защищён верификацией IP-адреса отправителя.
- **Тестовый/боевой режим:** Система ОБЯЗАНА поддерживать переключение между тестовым (`shopId` + тестовый ключ) и боевым режимами через конфигурацию (environment variable). Логика кода НЕ ДОЛЖНА зависеть от режима.
- **Хранение ключей:** `shopId` и секретный ключ ЮKassa ОБЯЗАНЫ храниться в environment variables. Хранение в коде, конфигурационных файлах или БД ЗАПРЕЩЕНО.
- **Суммы:** ЮKassa принимает суммы в рублях с копейками как строку `"100.50"`. Конвертация из внутреннего формата (копейки integer) в формат ЮKassa: `str(amount_kopecks / 100)` с 2 знаками после точки.
- **Валюта:** Только `RUB`. Другие валюты не поддерживаются.

### 8.2. SMS.ru / SMSC

**Назначение:** Отправка SMS-сообщений: OTP-коды для авторизации и уведомления о статусе заказа.

**Используемые API:**
- `POST /sms/send` (SMS.ru) — отправка одного SMS. Вызывается из SMS Worker.
- `GET /sms/status` — проверка статуса доставки (опционально, для логирования).

**Ограничения:**
- **Rate-limiting:** На стороне Core API (см. INV-012), НЕ на стороне SMS.ru. SMS Worker отправляет всё, что пришло в очередь. Защита от SMS-бомбинга — ответственность Core API.
- **Retry:** 3 попытки с экспоненциальным backoff (2s, 8s, 32s). После исчерпания — логирование, НЕ блокировка (см. §7.8).
- **Хранение ключей:** API-ключ SMS.ru ОБЯЗАН храниться в environment variable. Хранение в коде ЗАПРЕЩЕНО.
- **Содержание SMS:** Минимальное. OTP: "Код подтверждения: {code}. Aura Coffee". Уведомления: "{status_text}. Заказ #{short_id}. Aura Coffee". Не более 70 символов (1 SMS-сегмент для кириллицы). Длинные SMS = двойная стоимость.
- **Отправитель:** Настраиваемое имя отправителя (sender name) через SMS.ru. Требует верификации на стороне SMS.ru.

### 8.3. Яндекс.Карты

**Назначение:** Автокомплит адреса доставки (Suggest API) и проверка радиуса доставки (Geocoder API).

**Используемые API:**
- `GET /v1/suggest` (Suggest API) — подсказки адресов при вводе. Вызывается через Core API (проксирование, чтобы не раскрывать API-ключ на клиенте).
- `GET /1.x/` (Geocoder API) — геокодинг адреса в координаты. Вызывается из Core API при валидации адреса (см. §7.3).

**Ограничения:**
- **API-ключ:** Хранится в environment variable. Запросы к Яндекс.Картам проксируются через Core API. Клиентский фронтенд НЕ ДОЛЖЕН содержать API-ключ.
- **Rate-limits (Яндекс):** Бесплатный tier: 1000 запросов/день для Suggest, 1000 запросов/день для Geocoder. Для production — коммерческая лицензия. Система ОБЯЗАНА отслеживать потребление и логировать приближение к лимиту (80% порог).
- **Кэширование:** Результаты Geocoder API МОЖНО кэшировать (Redis, TTL 7 дней) — координаты адресов стабильны. Результаты Suggest API НЕ ДОЛЖНЫ кэшироваться (контекстно-зависимые).
- **Fallback при недоступности:** API считается недоступным при: таймауте ≥ 3000ms, HTTP-статусе 5xx или ошибке соединения (connection refused, DNS failure). Если Suggest API недоступен — показать обычное текстовое поле ввода адреса (degraded UX, но не блокировка). Если Geocoder API недоступен — ОТКЛОНИТЬ заказ на доставку с сообщением "Сервис проверки адреса временно недоступен. Попробуйте позже или выберите самовывоз." НЕ пропускать доставку без проверки радиуса.
- **Локализация:** Suggest API вызывается с параметром `lang=ru_RU` (для RU-интерфейса) или `lang=en_US` (для EN). Geocoder — всегда `lang=ru_RU` (адреса в РФ).

### 8.4. Сводная таблица секретов

Все API-ключи и секреты ОБЯЗАНЫ храниться в environment variables. Ни один секрет не должен попасть в код, git-историю или конфигурационные файлы.

| Переменная | Сервис | Описание |
|-----------|--------|----------|
| `YUKASSA_SHOP_ID` | ЮKassa | Идентификатор магазина |
| `YUKASSA_SECRET_KEY` | ЮKassa | Секретный ключ для API |
| `YUKASSA_WEBHOOK_IPS` | ЮKassa | Список доверенных IP для webhook'ов (или "все" в тестовом режиме) |
| `SMSRU_API_KEY` | SMS.ru | API-ключ для отправки SMS |
| `SMSRU_SENDER_NAME` | SMS.ru | Верифицированное имя отправителя |
| `YANDEX_MAPS_API_KEY` | Яндекс.Карты | API-ключ для Suggest + Geocoder |
| `DATABASE_URL` | PostgreSQL | Connection string (включает пароль) |
| `REDIS_URL` | Redis | Connection string |
| `JWT_SECRET` | Core API | Секрет для подписи JWT-токенов |
| `ENCRYPTION_KEY` | Core API | Ключ AES-256 для шифрования PII (телефонов) |
