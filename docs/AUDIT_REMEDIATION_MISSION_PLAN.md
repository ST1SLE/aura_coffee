# Audit Remediation Mission Plan

Date: 2026-04-30  
Source audit: `docs/audit-results/audit-report.md`  
Mission: turn the autonomous audit findings into a release-clean, GRACE-verified state without losing safety in parallel work.

## Mission Context

The audit showed that the isolated stack can complete the core happy path end to end: staff login, customer OTP, menu, cart, checkout, fake payment, pickup and delivery state paths, and courier assignment. The system is operational, but not release-clean.

The main blockers found were:

1. Customer frontend production build failed on unused TypeScript imports.
2. Runtime SMS order-notification tasks were discarded by the SMS worker as unregistered.
3. SMS log transport exposed raw phone numbers and OTP codes, violating INV-013.
4. Core API pytest was red because of stale tests and fixture drift.
5. `ruff check .` reported broad Python lint noise.
6. Customer/admin frontend lockfiles carried a moderate `postcss` advisory.

The audit also separated true runtime risk from test-harness drift:

- Live probes confirmed cart merge/patch/delete worked when using the same customer token.
- Live probes confirmed referenced-category delete returned `409` and preserved the category.
- SMS notification task registration and SMS log redaction were real runtime/security defects.
- Customer build failure was a release gate defect.
- Core API failures were mostly stale tests, fixture isolation, and deterministic env setup.

## Parallelization Decision

Parallel work is acceptable only by module boundary and write ownership. Depth of audit or urgency alone is not enough reason to parallelize. Each parallel packet must have:

- a dedicated git worktree and branch;
- a clear file ownership scope;
- an isolated `.env` generated by `scripts/setup-worktree-env.sh` if Docker may run;
- no shared lockfile or broad-formatting overlap with another active packet;
- its own verification commands;
- a final report listing changed files, tests, LDD marker assertions or why LDD did not apply, residual risks, and commit hash.

Parallel work is not acceptable for:

- broad `ruff` cleanup while functional Python packets are active;
- dependency lockfile updates that overlap with active frontend packets;
- GRACE artifact refresh while code packets are still moving;
- PDD or state-machine changes, because INV-016 requires sequential design review before implementation.

## Verification Gap Found During Wave 1

Wave 1 passed normal tests and direct redaction assertions, but it did not consistently enforce GRACE LDD assertions. This exposed a workflow gap: our instructions described LDD but did not make it a hard acceptance gate in worker prompts.

The workflow has now been tightened:

- `AGENTS.md` defines a hard GRACE verification gate.
- `.agents/skills/aura-grace/SKILL.md` requires LDD gate decisions and reporting.
- `docs/verification-plan.xml` includes `ldd-hard-gate` and `redaction-assertion-gate`.

From this point forward, a packet touching state transitions, transaction boundaries, auth/roles, OTP/SMS, payment webhooks, PII/secrets/logging, or required marker emitters must add/run LDD assertions or explicitly justify why LDD does not apply.

## Remaining Plan

### Step 1: Review Wave 1 Branches

Review before merging:

- `grace/audit-sms-worker`
- `grace/audit-customer-build`
- `grace/audit-core-tests`

Review checklist:

- Ensure no copied `.agents/` context or local `.env` files are staged.
- Check each diff for scope discipline.
- Confirm SMS redaction does not reintroduce any OTP-from-logs workflow.
- Confirm Core API changes are test-harness changes unless a product bug was explicitly proven.
- Confirm customer changes did not alter API behavior, pricing, auth storage, or dependency versions.

### Step 2: Add LDD Verification Follow-Up

Run a small sequential GRACE verification packet before final release confidence:

- For SMS worker, assert `[SmsWorker][send_otp][BLOCK_SMSRU_CALL]` with `GraceLogCapture` or a local `grace_logs` fixture.
- Assert captured logs do not contain raw phone, OTP code, JWT, API key, or SMS body for the touched SMS paths.
- Decide whether order notification task registration needs only structural Celery coverage or an additional marker in `docs/verification-plan.xml`.
- If a module lacks fixture wiring for LDD, add the narrowest local fixture instead of broad test refactors.

This packet should be sequential because it may touch the verification plan, SMS worker tests, and shared GRACE testing patterns.

### Step 3: Merge and Integration Gate

Merge order should minimize conflicts and preserve release gates:

1. SMS worker P0 branch.
2. Customer build gate branch.
3. Core API test-harness branch.
4. LDD verification follow-up, if implemented as a separate branch.

After each merge, run the narrow relevant gate. After all Wave 1 work is merged, run:

```bash
docker compose exec core-api pytest services/core-api/tests/ -v
docker compose exec sms-worker pytest services/sms-worker/tests/ -v
cd web/customer && npm run lint && npm run build && npm test
```

Use the canonical local entry point printed by `./scripts/up.sh`; ignore container-internal Vite URLs.

### Step 4: Serialized Cleanup Packets

These should run after Wave 1 merges:

1. **Python lint cleanup:** start with auto-fixable `ruff` errors, then handle F821 forward refs and import ordering manually.
2. **Dependency advisory:** update `postcss` in both frontend lockfiles, then rerun frontend audit/build/test.
3. **GRACE artifact refresh:** update `docs/development-plan.xml`, `docs/verification-plan.xml`, and `docs/knowledge-graph.xml` only where completed code changes made them stale.
4. **Final phase gate:** run full backend tests, shared/payment/SMS worker tests, both frontend test suites/builds, and a smoke stack check.

## Rollback Strategy

Each packet is isolated by branch. If a merge regresses behavior:

- revert the merge commit for that packet;
- keep unrelated completed branches intact;
- rerun the narrow gate for the reverted area;
- only then proceed to the next merge.

Do not use destructive reset/checkout operations on the main worktree while user changes or untracked audit artifacts are present.

## Success Criteria

The mission is complete when:

- Wave 1 fixes are reviewed and merged.
- Required LDD assertions are present or explicitly justified for touched GRACE-sensitive paths.
- Core API, SMS worker, customer frontend, and admin frontend gates pass.
- `ruff check .` is either clean or has an explicitly accepted residual list.
- `npm audit` no longer reports the `postcss` advisory, or the risk is documented with a pinned reason.
- GRACE artifacts match the final code behavior and verification policy.
